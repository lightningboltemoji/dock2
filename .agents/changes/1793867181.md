# Clipboard History's shortcut toggles

> Change `1793867181` — 2026-11-05

## Goal

`1793866893` gave Files a shortcut that toggles and left Clipboard History's as the odd one out: pressed twice, it stacked
a second screen, and leaving took two Escs. Asked to make it match.

## Implementation

`toggleClipboardHistory` is the shortcut's action: on top it pops, back to wherever the view came from, and otherwise it
shows. Files' shortcut gets that rule from its tile, and Clipboard History has none, so here it is stated outright. A
filter typed goes with the view, as whatever is open inside a tile's view does.

`showClipboardHistory` built a new `NodeScreen` each time, so `ViewsController.push`'s rule of one screen once could not
see it was the same view. It now finds the one on the stack by its host, through a new `screens`, and pushes that, so a
press with Files over it brings it back rather than stacking a second. Rejected: a weak reference kept in
`InteractionController`, which is a second record of what the stack holds and depends on the screen being released on
time, or a closed screen gets pushed again. Asking the stack has nothing to keep in step.

`push` also takes the case of a screen already on top, which it only focuses. That is what keeps `dock2 clipboard` twice
from clearing a filter, and it let `showFiles` lose its own branch for the same thing. `dock2 clipboard` stays one-way, as
`dock2 files` does, and so does the command in search.

The change to the `help` text regenerates `config.example.toml`. In `IMPLEMENTATION.md`, the control section said `files`
and `clipboard` were the tile's and the shortcut's paths, which has not been quite true of Files since it toggled, so it
now says they open and never close.

Driven as `1793866893` was, with real chords and on history off, so no run reads the store. From rest, from an empty field,
over a query (back with its 7 rows), and opened by the command (back to its query), one press opens and the next closes.
A filter closes with it. Over Files it closes back to Files. Under Files it comes back, and alternating the two shortcuts
five times left one Esc to rest, which is the stack holding one of each at most. `dock2 clipboard` twice kept its filter
and left one screen. `dock2 files`, twice and then to a folder, left one too. A capture confirmed the view draws once
brought back. A filter covered by Files and brought back is cleared in the host as well as the field: the empty state,
which depends on the host's query, went from "No results" back to "Clipboard history is off". `picks.json` and `usage.json`
were restored after the ↩.

## Observations

- With history off, every run saw the empty state. Nothing here exercised rows, a preview, or a selection kept across
  being covered and brought back.
- Quick Look of a copied file is a screen of its own on top of Clipboard History, not part of it, so a press there closes
  Quick Look and the next closes the history. Files' Quick Look lives inside Files and goes with it in one. That follows
  from the code and was not driven, since a copied file needs the real store.
- Brought back from under another view, the undo manager's deletes stay, since the host is the same one. That follows from
  the code and was not driven either.
- Plugin views still stack: each `showPluginView` makes a new screen, and a command's shortcut opened twice pushes twice
  unless the plugin says otherwise. A plugin decides what its command does, so the rule here doesn't obviously apply.
- Still no test target for `Dock2Shell`, so the toggle and `push` rest on these runs.
