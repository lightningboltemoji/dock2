# Apps open in the session's environment

> Change `1792807190` — 2026-10-23

## Goal

An app opened from dock2 inherited the environment dock2 was started with. Started from a shell inside
Claude Code, dock2 handed Ghostty that shell's `CLAUDE_*` variables, its `PATH`, `TERM`, `PWD` and the rest.
How dock2 was started should not change how the apps it opens start. Opened from dock2, an app should start
as it would from the Dock or Finder.

## Implementation

Measured with a probe app that writes its own environment to a file and exits. LaunchServices passes the
caller's live `environ` to the app it launches, layered over launchd's session environment. `NSWorkspace.
OpenConfiguration.environment` only adds keys on top: set to `[:]` or to one variable, the caller's whole
environment still came through. A caller that empties its environment at runtime (`unsetenv` on every
key, after AppKit is up) launches an app whose environment is byte-identical to one Finder launches:
launchd supplies `PATH`, `HOME`, `SHELL`, `TMPDIR`, `SSH_AUTH_SOCK` and the domain's `launchctl setenv`
variables.

So the boundary is the process, not each call. `LaunchEnvironment.setAside()` runs once in `main`, on the
app's path only, before the logger, the lock or AppKit. It captures `ProcessInfo.processInfo.environment`
into `LaunchEnvironment.variables` and unsets every key. Every launch path is covered at once, the ones
that exist and any added later: tile clicks (`openApplication`), Files, search, Open With, drops on a tile,
clipboard entries and plugins' `open`. dock2's own reads go through `variables`: `DOCK2_DEBUG`,
`DOCK2_APPEARANCE`, the display switches, `DOCK2_FULL_DISK_ACCESS`, `DOCK2_KEY_STORE`, and `DOCK2_SOCKET`
or `TMPDIR` for the control socket. `ControlWire.socketPath` loses its `ProcessInfo` default, so no caller
can silently read the emptied process environment and bind a socket the CLI never dials.

The CLI verbs, `--restore` and `--guard` keep their environment. They open no apps, and `screencapture` and
`log stream` run from them as any shell tool's children do.

Rejected:
- **Passing an environment per call.** It cannot remove a variable, as measured above.
- **Launching through a clean `/usr/bin/open`.** That costs a process spawn per click, gives up the
  completion handler and the `NSRunningApplication`, and still leaves `NSWorkspace.open(url)` call sites
  to route.
- **Swapping `environ` around each call.** That is not thread-safe.
- **Rebuilding launchd's environment by hand** (a hard-coded `PATH` and so on). It duplicates launchd and
  drops the user's `launchctl setenv`.

## Observations

Verified live with the debug build started from a Claude Code shell (`DOCK2_DEBUG=1`, about 50 variables).
`dock2 status` reported `debug: true` and the socket at `$TMPDIR/dock2.sock`. EnvProbe.app, opened from
Files, got Finder's environment plus `__CF_USER_TEXT_ENCODING`, which CoreFoundation sets inside dock2's
process. A Dock-launched Ghostty has it too. No `CLAUDE_*`, `DOCK2_*` or `TERM*` came through. `kill -9`
of dock2 then left the guard (now started with an empty environment) to give everything back: the journal
was gone and `com.apple.dock` was identical to its state before the run.

The `openApplication` path itself (a tile click) was measured with the standalone probe launcher rather
than through dock2, since both pinned apps were running.

dock2's own children now start with an empty environment: the guard, the Now Playing `perl` helper and
`log show` for Collect Logs. None reads one, and Foundation resolves the home and temporary folders
without `HOME` or `TMPDIR`. A future child that needs a variable must be given it explicitly from
`LaunchEnvironment.variables`.

`ps eww` on dock2 still shows the environment it was started with: it reads the original block from the
process's arguments area, not the live `environ`.
