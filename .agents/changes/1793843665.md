# Waiting for what a plugin test depends on

> Change `1793843665` — 2026-11-04

## Goal

`release` failed at Test on `85ea92b`, so nothing published and `tip` stayed behind `main`. The failure was
`revokingRunEndsWhatRuns`: `"error: run was revoked"` never arrived. It was the first run of that test on a
runner, and at runner speed it fails every time. Behind it was a wider fault: tests that paused for a fixed time
and then checked were betting the machine was fast enough.

## Implementation

The test revoked `run` too early. It waited for the process to be held with `settle`'s default of 0.2 s, but
the first event starts the instance, and each test compiles the guest into a temp folder of its own. That takes
longer than 0.2 s on a runner. `settle` returns quietly when its time runs out, so the test revoked `run` before
the effect arrived. `resources.end` found nothing to end, the effect was then refused (`run is not granted`, in
CI's log straight after the test started), and the plugin correctly heard a different error from the one the
test wanted. dock2 behaved as designed; only the test was wrong. The test's 3.219 s is both waits timing out.

Every fixed pause whose result depended on speed is gone, 19 in all, and each went by what it
was waiting for:

- **One hop, or "nothing else happened":** `TestHost.answered` sends an `echo` and waits for it. The instance's
  queue and the main queue keep their order, so it comes back behind every earlier answer. This makes "exactly one"
  and "nothing else" checks exact, which no pause could.
- **Two hops:** a refusal comes back as a second event, which an `echo` sent beside it would overtake, so these wait
  on the toast.
- **No wait needed:** `aPluginSwitchedOffHearsNothing` checks that no instance exists, since `send` refuses
  synchronously. `onlyTheUserOrWhatTheyAskedForSummons` ended on a pause with nothing after it.
- **Mid-stream:** `revokingLocalNetworkEndsAStream` paused 0.3 s and hoped the stream had begun. The guest now says
  `heard <request>` on a stream's head and the test requires it, so the premise is checked.
- **The file watcher:** `theFileIsWatched` polls, with the idiom `ClipboardStoreTests` already uses.

`settle` has neither default now, so a wait states its time and a bare pause does not compile. A wait that is met
returns at once, so its ceiling is a hang detector and costs a passing run nothing. The premises above `#require`,
so an unmet one fails as itself rather than lines later as a missing toast.

Rejected: a test-only drain on `PluginHost`, since `echo` needs no production surface, and a fake scheduler, which
would stop exercising the threading these tests exist to check.

Measured with `taskpolicy -b swift test --skip-build --filter Dock2PluginsTests`. Background priority alone takes
the 86 tests to about 13 s against CI's 12.2 s, where a normal run takes 5 s. Saturating the CPU at normal
priority does not reproduce it, and adding load on top of background priority (about 60 s) fails unrelated tests.
`revokingRunEndsWhatRuns` failed 4 of 4 before and passed every run after. Over 10 plugin runs and 3 of every
target, the only failure was the budget test below. To check the rewritten negatives still catch something, four
guards were removed at once: `answer`'s, `send`'s `isEnabled`, `choose`'s `after != before` and
`choicesChangedInFile`'s `heard`. `aRequestWhoseCapabilityIsRevokedIsToldSo`, `aPluginSwitchedOffHearsNothing`,
`aPluginIsToldWhatItHolds` and `aShortcutEditedInTheFileRestartsNothing` each failed on the line that covers it.

## Observations

- Not yet proven on a runner: the first proof is the next push to `main`.
- That recipe matches CI in total time, not in kind. Single-threaded work is far slower than on the runner:
  `aLargeVaultOpensInSlicesEachWithinTheBudget`'s longest slice was 508–978 ms there and 313 ms on CI, so it often
  fails under the recipe against its 800 ms limit. That says nothing about CI. Budgets run on the wall clock on
  purpose, so this one is a performance test and was left alone.
- `revokingLocalNetworkEndsAStream` does not prove the stream stopped. `http stream` could only arrive when the
  stream ends about 3 s later, and the check runs well before that, as it always did. `cancel` delivers nothing, so
  it is not `answer`'s guard that keeps it quiet. A real check would watch the server see the connection close.
- Sleeps that remain are not bets. `ControlSocketTests` is quiet past a deadline, so time is its subject.
  `SettingsStoreTests`' 50 ms and `PluginInstanceTests.settle`'s 20 ms follow work already on the main queue, whose
  order decides the result.
- `aCommandRunsItsSlotsAsArguments` took 2.1 s of its 3 s ceiling on CI, as the first test of a suite with the
  others running beside it. Other waits in `PluginRunTests` keep 3 s. Compiling the guest for each test is most of
  what they absorb; a cache shared across a run would shrink it.
