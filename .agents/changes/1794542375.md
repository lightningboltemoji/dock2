# The selection after ⌘⌫

> Change `1794542375` — 2026-11-12

## Goal

After ⌘⌫ or ⌥⌘⌫ in Files, the trashed rows' selection was dropped when the folder's new listing came in, and
nothing replaced it, so every delete left the keys with nothing to act on. Finder moves the selection
instead. This change gives Files the same rule.

## Implementation

The rule was measured in Finder on macOS 27.2 in the `golden-gate-base` VM, in column view and list view.
Rows were clicked with ⇧ and ⌘ through `drive`, ⌘⌫ sent, and the selection read back through Finder's
AppleScript `selection`. Finder selects the item after the *lowest* selected item in display order,
whatever order the items were clicked in: {2, 5} → 6, {5, 2} → 6, {6, 3, 4, 5} → 7, {7, 3} → 8. When the
selection includes the last row, nothing is selected ({8}, {7, 8}, {1, 8}, {2, 4, 8}). Focus stays in that
column, and from there ↓ takes the first item and ↑ the last. A folder that receives the selection opens its
column. ⌥⌘⌫ behaves the same way. List view gave the same results for {4}, {8}, {2, 5}, {7, 8} and {1, 8}.
When another process removes a selected file, Finder just drops the selection, and ⌘Z selects the restored
items. Files already did both.

`FilesState.successor(of:in:)` in Core holds the rule. `FilesScreen` computes the successor when the key is
pressed, because by the time the operation finishes the new listing may no longer show where the trashed
items were. It applies the successor when `done` arrives, and only if three things hold: the items were the
whole selection, the selection now holds nothing but items that went (empty, if the watcher's prune ran
first), and the successor is still listed in the focused column or in the results. That leaves alone a
right-click trash of an item outside the selection, a selection the user moved during a long trash, and a
trash that failed partway, where what is left stays selected. A column that has since gone elsewhere does not
list the successor, so the check also covers navigation, except for a second tab showing the same folder.

To know what went, `trash` and `delete` now pass the URLs they removed to `done`, as far as they got, in the
same way `copy` passes what it made. `Interrupted.keeping` now carries `made` without a record, because a
partial delete has no record. No existing caller has one without the other.

Search results were a snapshot, so trashed items stayed listed. `removed` now drops what went from
`search.results` and applies the same rule there. ↑ from the search field with nothing selected now takes the
last result, as the table's own ↑ does. ⌘⌫ only reaches results once a click has put the keys in the list,
since the field owns ⌘⌫ while it is being edited.

Rejected: moving the selection when the key is pressed, before the trash runs. A failed or cancelled trash
would leave the selection on the successor and off the items that are still there.

Verified on the debug build in the same VM by reading each table's `AXSelectedRows`: all 13 of the
measured column cases, the folder case, ↑ and ↓ after a bottom delete, ⌥⌘⌫ through its confirm, trashing a
result including the last one, ↑ from the field, a right-click trash outside the selection, and ⌘Z.

## Observations

- Measured only on macOS 27.2. Not checked on macOS 26 or earlier.
- Icon and gallery views were not measured, since Files has neither.
- A failed trash in Finder (a locked file, for example) was not measured. Files keeps the selection on what
  is left.
- A second tab showing the same folder with nothing selected could take the successor if the user switched
  to it during a long trash.
