# A view that starts on an item

> Change `1794450858` — 2026-11-11

## Goal

A plugin's list or grid always opened on its first item. An agenda wants to open on today, a player's queue on
the track playing, and any long view on where the user last left it. Plugins needed a way to name the item a
view starts on, without that ever fighting the user once they move.

## Implementation

`ListNode` and `GridNode` gain `selected`, an item id. Each component remembers the last `selected` it was
given and takes a new one only when it differs. That is the whole contract: a plugin that renders its node from
state on every redraw names the same item each time and never pulls the selection back, while one that names
another item moves it. The rejected alternatives:

- **Taken on every update**: any plugin redrawing as data streams in — a sync, a server's pages — snaps the
  selection back under the user's arrows.
- **Two-way, the plugin told each move** (a controlled component): every arrow press becomes a wasm call, and an
  update that crosses a move in flight pulls it back anyway.
- **An imperative `select` effect**: the right tool for "jump to now" pressed repeatedly to the same item,
  which the edge rule can only do by an update naming nothing in between. Nothing asks for that yet, so it
  stays out until a plugin does.

A named item not yet among the rows — a list that opens loading and fills later — stays pending, and is taken
the moment it shows, unless the user typed or moved first. Typing clears it only when the query actually
changes, since the field is reset on every screen shown. A taken item out of sight is brought to the middle
rather than to the edge, so both what comes before and after are visible. That centring waits for the rows to
have a height (`RowsView.centring`, re-run from `layout`), since a screen's first `show` can come before its
slot has sized it. The grid does the same from its own `layout`.

`viewClosed` now carries the item selected when the view closed (`Component.selected`, through
`ViewHost.closed(selected:)`), so a plugin can store it and open there next time. Clipboard History, the other
`ViewHost`, ignores it.

The demo gains Starts in the Middle (forty weeks of days, opened on today) and Starts Partway Down (a grid
opened on cell 130). Both open where they were left, through a `resume` hook the demo's screen trait gained, and
each has ⌘K actions to name another item and to redraw naming the same one.

## Observations

- Seen in a VM: the agenda opens on week 21's Wednesday, centred; a move followed by Redraw stays; Name a Week
  Later moves to the next Wednesday, centred; closed on a Thursday and reopened, it opens there. The grid opens on
  cell 130, centred, and a move survives Redraw.
- Not seen live: an item named while the list is still loading and taken when it fills. No demo screen does
  that, and the shell's components have no tests.
- A plugin that wants to select the same item again, after the user moved away, must send an update without
  `selected` first. An explicit effect is the fix if one ever needs it.
