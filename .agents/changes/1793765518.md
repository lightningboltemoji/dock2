# `xpc`: messages to the services a plugin names

> Change `1793765518` — 2026-11-03

## Goal

The fourth step of the capabilities plan (`design/plugins.md`). A plugin that wraps an app's own agent had
no way to talk to it. The product's [services](../product/plugins/permissions.md#services) reach a service by
its Mach name, only while it is signed by the team the manifest names, and tell the service which plugin
speaks.

## Implementation

**The connection** (`PluginXPC`, Dock2Plugins) is opened at a plugin's first message to a service and is
held under `xpc` like any live resource, so revoking or stopping cancels it. It is made with
`xpc_connection_create_mach_service`, privileged for `"daemon": true`, with
`xpc_connection_set_peer_code_signing_requirement` set to `anchor apple generic and certificate
leaf[subject.OU] = "<team>"`. That holds for Developer ID, App Store and development certificates alike.
How a connection is made is a closure, so the tests point it at an anonymous listener of their own.

**Effects and events.** `xpcSend(request?, service, message)`: the message must be a dictionary, and
`dock2.plugin` is set to the plugin's id over whatever the plugin put there. With a request id the reply comes
back as `xpcReply`, or as an `error` after 30 s. The timeout is a `DispatchWorkItem` cancelled by the reply,
by a revoke, or by a second request under the same id. What the service sends unasked is `xpcMessage`, and
the connection's errors are `xpcClosed`: `interrupted` (the service went and may come back, so the plugin can
send its state again) or `invalid` (gone, or refused by the requirement), after which the next send opens
afresh. Events from a connection reach the plugin only while it is held.

**Values** are tagged in Core (`XPCValue`, with `JSONValue` for what a plugin hands over as-is). A whole
number is an int64 and any other a double. `{"$int"}`, `{"$uint"}` (a string past `Int64.max`),
`{"$double"}`, `{"$data"}` (base64), `{"$date"}` (milliseconds since 1970) and `{"$uuid"}` say otherwise.
A single-key object whose key is not a tag stays a dictionary. Back to the plugin every number is tagged, so
it reads the type the service sent. A reply holding a file descriptor, shared memory, an endpoint or any
type a plugin cannot hold is refused whole. The SDK's `XpcValue` writes and reads the tags.

**Measured**, against a LaunchAgent bootstrapped into this user's domain for the purpose: an ad-hoc-signed
probe claiming `zip.tanner.dock2.probe-agent` answered a plain connection by that name, and the same
connection with the requirement for team `ABCDE12345` got "Peer Forbidden" without the agent hearing a
word. The tests show the same against an anonymous listener in the test process, which is signed ad hoc.

## Observations

- No service signed by a real team was reached: this Mac has no signing identity to make one. The
  requirement's passing case is Apple's documented form, unexercised here.
- A daemon's service (`"daemon": true`) was not tried: bootstrapping one needs root.
- `NSXPCConnection` stays the product's _Next_: a protocol built at runtime is refused by
  `NSXPCInterface` (`design/plugins.md`).
- A plugin may send to several services; each is one connection. A service sending without end is not
  limited beyond what the plugin's background budget makes of each event.
