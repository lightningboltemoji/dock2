# Compiling the test guest once a run

> Change `1794898554` — 2026-11-16

## Goal

`release` failed at Test on `98204e2` (run 44012569729), so nothing published. The failure was
`aSlotStartingWithADashOrOutsideItsFoldersIsRefused`. At its 3 s ceiling the recorder held only `started with 1
settings`, and the test took 4.264 s. The commit (Files and Quick Look) touches nothing it tests. The runner was
slow: the plugin run took 16.5 s, against 8.8–14.7 s in the five green runs before it, and
`aCommandRunsItsSlotsAsArguments` used 3.156 s of the same 3 s ceiling. `1793843665` saw this coming. Each test
compiles the guest into a cache of its own, so every first event pays for compiling it, and the test's wait times
that compile. Since `1794536247` (Pulley → Cranelift), that compile is native code generation.

## Implementation

`TestGuest.compiled` compiles the guest once per run, using an instance of its own that is sent one `echo` and
drained. `TestGuest.precompile(into:)` copies the result into a store's `cacheDirectory`. `TestHost.make` and
`PluginHostTests.store()` call it, so a test host starts the way a dock2 that has run the guest before does, and
its first event reads the module back. The compile goes through `PluginInstance` itself, so the file's name and key
stay in `loadModule`, the only place that knows them. Each test gets a copy rather than a shared directory, so
`removeCompiled` and a store's `remove` in one test cannot touch another's cache.

Measured with temporary timing in `PluginInstance.run`, under `taskpolicy -b swift test --skip-build --filter
Dock2PluginsTests`, two runs on each side. Before: 41 compiles a run, averaging 633–664 ms and peaking at
1.29–1.32 s while they ran concurrently. After: 6 compiles (the warm-up, plus tests that build their own instance
or install the guest) and 38 read-backs averaging 3 ms. The warm-up took 265–335 ms. The failing test went from
0.72–1.12 s to 0.05–0.10 s, and the plugin run from 10.3–13.1 s to 6.4–7.0 s (4.2 s at normal priority). `make
test` passed. As with the earlier fixes, the failure itself did not reproduce locally.

Rejected:

- Raising the 3 s ceilings. They are hang detectors and a met wait costs nothing, but the time they would absorb
  is compiling, which is not what any of these tests is about. That compile also grew with the runner's load.
- Pointing every store at one shared cache, through a `PluginStore` parameter or a symlink. Tests running at the
  same time would share a directory that `removeCompiled` prunes, and dock2 would gain a parameter only tests use.
- Making `loadModule` internal so the warm-up could call it. `deliver` and `drain` already reach it without
  touching production code.

## Observations

- Not yet proven on a runner: the first proof is the next push to `main`, which also publishes what `98204e2` did
  not.
- The first test to build a host waits on the main actor for the warm-up, and so do the other main-actor tests
  that start beside it. The wait happens before any test's clock starts.
- `PluginInstanceTests` and `BitwardenBudgetTests` still compile into caches of their own, on purpose:
  `theCompiledModuleIsCachedAndReadBack` tests that path. Their waits drain the queue instead of timing out.
- The 26 ms in `IMPLEMENTATION.md` is an uncontended compile. Concurrently, under background priority in the test
  build, the same compile reached 1.3 s. That figure was left alone; what several plugins compiling at once at
  launch costs has not been measured.
- `dock2-compiled-<uuid>` is left in the temp folder, like each test's own folder.
