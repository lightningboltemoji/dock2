# A click on a selected folder closes what was open inside it

> Change `1794885733` — 2026-11-16

## Goal

With `Seek › a › b › c` open and `deep.txt` selected in `c`, a click on `b` in `a`'s column changed nothing: `c`'s
column stayed open, `deep.txt` stayed selected, and the path still ended at `deep.txt`. Finder takes that click as
going back to `b`.

Finder was measured in the `golden-gate-base` VM (macOS 27.2), column view, over `Seek/a/b/c/deep.txt` with a file
beside each folder:

| Click, with `deep.txt` selected in `c` | Finder |
| --- | --- |
| `b`'s row in `a`'s column, off its name | `b` selected with the keys, its column open with nothing selected, `c`'s column gone; the title `b` |
| `a`'s row, two columns back | the same, at `a` |
| `c`'s name in `b`'s column | the same at `c`, then the name turns into a rename field after the double-click interval |

## Implementation

- **`ColumnTable.mouseDown`**: a plain single click, not a drag, on a row already selected leaves the table's
  selection as it was. The table posts no selection change for it, so the click never reached `FilesState`.
  `ColumnTable` now reports that case itself (`onReselect`), and `ColumnView` passes it on as `onSelect` with the
  selection unchanged. `FilesState.select` already does Finder's part: it trims the columns past the one clicked,
  opens the folder afresh, and gives that column the keys. A test pins that rule. The click must be a single click:
  the second click of a double-click opens the folder in place, and reporting it would undo that.
- **The slow-click rename** checked "on the name" after the click had been acted on. The reselect re-renders and
  scrolls the strip, so the click's window point then mapped to a different place in the cell, and the rename never
  started. The check now happens at `mouseDown`, before anything moves.
- The rename's `window?.firstResponder === self` test is true for any clicked column, since the window gives a table
  the keys before its `mouseDown`. A slow click on a selected name in a column without the keys therefore renames.
  That is what Finder does, as measured, so the rename now runs alongside the pop as it does in Finder. The test was
  left in place: a click that doesn't take the keys, in a window that isn't key, is not measured.
- The NSTableView single-click `action` was the other place to hear this click. It fires for every click, including
  ones that change the selection and the first click of a double-click, so the filtering would have moved to
  `ColumnView` with less to go on.

## Observations

- Verified in the same VM, on a debug build:
  - a click on `b` off its name, with `deep.txt` selected, gives `Seek › a › b`: `b` has the keys and `c`'s column is
    gone;
  - a click on `c`'s name pops at once and opens the rename half a second later. Esc cancels it and `c` keeps its name;
  - a slow second click on the selected `deep.txt` in its own column still renames, with no pop;
  - a double-click on `b` opens it with `c` selected.

  The baseline build showed the bug on the same click.
- A drag that starts on a selected row moves more than 4 pt, so it is not taken as a reselect. That follows from the
  guard and was not driven.
- In ⌘F's results list, a reselect re-sets the same selection, which renders nothing new.
