# Plugin storage on SQLite

> Change `1794451662` — 2026-11-11

## Goal

A plugin's storage was one `PluginData/<id>/storage.json` of string keys to string values, read whole from disk on
the main thread for every get and encoded and rewritten whole, atomically, on the main thread for every set.
Bitwarden keeps its synced vault, up to an HTTP body's 16 MiB, as one value, so setting its device id rewrote the
vault too, on the thread that draws the Dock. Nor could a plugin read several keys, list what it holds, or write
more than one key at once and know they landed together.

## Implementation

**The store.** `PluginStorage` is SQLite through the system's `SQLite3`, `storage.db` beside where `storage.json`
was: one `WITHOUT ROWID` table, `key TEXT PRIMARY KEY, value BLOB`. Values are bound as bytes, so `length(value)` is
read from the record header without loading a vault. `WITHOUT ROWID` measured at 21 bytes an entry for 13-byte
keys and empty values against 47 for a rowid table with its separate key index; with three 16 MiB values among
10,000 small ones, both schemas wrote a vault in 0.04 s and scanned keys in under 0.01 s, so the large-row warning
in SQLite's documentation costs nothing here. Keys are `BINARY`, memcmp over UTF-8, which is the order of their
scalars.

**Ranges.** A prefix is `key >= prefix AND key < end(prefix)`, `end` stepping the last scalar up one rather than the
last byte: a byte step can make invalid UTF-8 (`0x7F` to `0x80`) that SQLite would compare but that no string is.
U+D7FF steps to U+E000 over the surrogates; a last U+10FFFF is dropped and the scalar before it stepped; "" and a
prefix of U+10FFFF alone have no end. `after` replaces the lower bound going forward, the upper going back, only
when it lies inside the range, so each side has one bound: a second `key > ?` alongside `key >= ?` is only a
filter to SQLite's planner, which would scan from the prefix to the cursor on every page. The statements are built
from fixed fragments, every key and value a parameter, and prepared once a connection.

**No SQL for plugins**, as agreed: `ATTACH` and pragmas would be sandbox to defend, a dialect would join the
versioned interface, and a plugin is the one writer of its store, so it needs atomicity, not isolation.
Secondary indexes are left to the plugin, keys of its own in the batch they index; `runtime.md` says so.

**The wire.** Named after `files`' effects: `storageRead` → `storageRead`, `storageList` → `storageListed`,
`storageWrite` → `storageWritten`. A write's steps are one key naming which, as an icon is (`{"set": k, "value": v}`,
`{"delete": k}`, `{"deletePrefix": p}`). `storageList` carries a `StorageListing` decoded from the effect's own
object, as `derive` carries a `Derivation`. `storageRead` was going to answer with a dictionary; it answers with a
list of entries in the order asked, because Swift's `String` equality is canonical equivalence: a `[String:
String]` would hold "é" and "e\u{301}", two keys to SQLite, as one. A missing key is left out rather than listed
without a value, so `value` absent means only "keys alone" in a page. The single-key three are unchanged on the
wire and run as a one-key read and one-step writes; their answers are now held like any request's.

**Threading.** As secrets do: a serial queue per plugin and the answer hopped back to main through `answer`, held
with `waitOn` under no capability, so an outstanding read keeps the instance from unloading and a stop drops the
answer. A write already asked still lands after a stop: storage needs no grant a revoke could take back, and
dropping it could leave a plugin's own index out of step with what it indexes. The host keeps one `PluginStorage`
per plugin for its life, closing the database as the plugin stops or unloads but keeping the queue, so a write
queued before a stop is never overtaken by a read after the restart. `stopAll` drains every queue as dock2 quits;
`remove` drains after `stop`'s close, so the database is closed and its WAL checkpointed before `PluginStore.remove`
takes the folder, and the three files with it. macOS's SQLite keeps its WAL files across a close, `-wal` emptied,
as a run in a VM showed after a quit. A write without a request that fails is told to
the plugin only if it is still loaded, rather than starting it to hear about an older instance's write.

**Atomicity.** Each batch is one `BEGIN IMMEDIATE` transaction; WAL with `synchronous = NORMAL` keeps that across a
crash and risks only the last commits to a power cut. Checked by killing a `sqlite3` process with `kill -9`
mid-batch, after it had deleted every row and spilled 267 MB of inserts into the WAL: the store reopened with
`integrity_check` ok and only the row from before.

**Limits** (`PluginStorage.Limits`):

- *A value, 24 MiB.* A whole 16 MiB HTTP body fits as text, as Bitwarden keeps it, and as base64 (21⅓ MiB), with
  room under the guest's 64 MiB to read one back: the event's escaped JSON and the decoded string are both in its
  memory at once, about 50 MiB for a 24 MiB value of JSON text. 32 MiB would not leave that room. (Estimated, not
  measured in the guest.)
- *A plugin, 256 MiB.* Ten whole-vault values; past that a plugin wants files, not a key-value store in dock2's
  folder. An entry costs its key, its value and 16 bytes: random 21-byte keys with empty values measured 30 bytes
  an entry on disk, 4-byte keys about 12, so without it a store of tiny entries could take several times its
  quota. The cost is measured as the database opens (one `sum` over the table) and kept as batches change it. A
  batch is refused only if it grows the store past the quota, so one already past, carried in from a large
  `storage.json`, can still shrink.
- *A key, 1 KiB.* Keys are names, and come back in every page and as cursors; a longer one should be hashed.
- *A page, 1,000 entries or 4 MiB*, the limit a plugin names held to it, and 1,000 when it names none. A page ends
  before the entry that would take it past 4 MiB but always holds one, or a value past 4 MiB could never be listed.
  4 MiB keeps a page's event a small part of the guest's memory; how long the interpreter takes to parse one was
  not measured. A read of several keys is bounded only by the quota, since a plugin knows what it stored.

Past a limit, the batch is refused whole: the key and value limits before the transaction, the quota after its
steps, which roll back. The refusal is the existing `error` event under the request, as `refuse` sends.

**Carrying `storage.json` in.** As the database first opens, its keys over the database's in one transaction, then
the file removed. A crash between the two carries it in again over a database nothing has written since; an older
build run in between writes a new one, which wins on the next launch. An unreadable file is warned about by
`JSONFile` and removed, as it would have been overwritten before.

## Observations

- Seen live in a VM through the demo's Kept Notes, a screen added for it: notes listed by prefix a page at a time
  as it opens, three kept by ⌘N with each write's answer toasting, all of them back after dock2 quit and started
  again, and every one gone in one `deletePrefix`.
- The test guest covers one event's write, read and page in order, refusals under a request and without one, a
  stop dropping answers but not writes, and removal taking the database. The store's own tests cover byte order,
  the awkward prefixes, paging both ways, the page's bytes, the limits, the quota across a reopen, and the import.
- A database SQLite cannot open, or finds corrupt, is reported to the plugin as an `error` on every storage effect
  and never moved aside. `storage.json`'s answer to that was to start afresh; a store the plugin may have indexed
  deserves more thought than that.
- The WAL is not size-limited while a database is open; it grows to a plugin's largest write and is emptied when
  the database closes, at the latest three minutes into idleness for a plugin with no tile or view.
- Bitwarden is unchanged and still keeps its vault as one value. Splitting it into `item/<id>` entries in one
  batch would let a sync rewrite only what changed.
- A `storageRead` naming a key twice answers it twice; requests sharing an id behave as any request's do, the
  later one's answer dropped.
