# Icons for any tile

> Change `1794556735` — 2026-11-12

## Goal

Only the Finder tile could wear an icon of the user's, and only one of Cairo's pictures. [icons](../product/icons.md)
lets any tile wear either a picture or an Icon Composer icon, compiled. The icon shows wherever dock2 shows the app as
an app. It is set in `[icons]` and in a new Settings → Icons section, and a tile's menu reaches it through Change Icon….
The Finder tile is now the Files tile, since that is what it opens.

## Implementation

The design is [design/icons.md](../design/icons.md) as it stood before this change. Its premises were measured again
here before building. Calculator's `Assets.car` in an executable-less `.appex` shim draws within 3 levels in 255 of
Calculator's own icon at 512 px, and `assetutil --info` takes 17 ms a catalog.

- **TOML.** `[icons]` entries are inline tables written whole. `TOMLDocument` could change a key inside an inline table,
  but it could not replace or remove the whole table. That is because the parser stores `a = { … }` as a table, which
  has no span. A table written as a whole statement now keeps its statement's span (`TOMLTable.span`), so `set` and
  `remove` treat it as a value. `TOMLValue.table(_:)` builds one to write, in the order its keys were given:
  `{ picture = "pear", color = … }` rather than sorted. A table that was read still spells sorted, since `spelled`
  is how the store compares `[plugins]` across reloads.
- **Core.** `TileIcons.read` reads `[icons]` inside `Settings.read`, so a shape it can't read is an ordinary
  diagnostic: in the log, in `dock2 config check`, in Settings. An entry with any mistake is left out whole, and its
  tile wears its own icon. The same app keyed twice under different spellings of its bundle id is a diagnostic on the
  second. `AppRef(written:)` is shared with `pinned`'s codec, so the two key apps alike. `IconCatalogContents` reads
  `assetutil`'s JSON. `FinderIcon` became `PictureIcon` without its optional. `Settings.finderIcon`, its three
  `files.icon*` keys, the `"finder"` picture codec and the defaults-domain import of `finderIcon` are gone, with no
  migration (pre-alpha).
- **System.** `TileIconFiles` hashes each named file whenever `[icons]` changes. It keeps what `assetutil` found by
  hash in `Icons/catalogs.json`, so at any launch after the first the dock draws every file icon from its first
  frame. Only a file never seen waits for `assetutil`, and its tile wears its own icon until then. This replaces the
  design's in-memory cache: in memory alone, every launch would draw the apps' own icons and then swap them. The first
  resolution with nothing waiting prunes the shims and records no entry names. `AppDirectory` takes the picture
  drawer from the shell (`PictureIconImage` needs `IconPlate`, which is AppKit drawing in Shell). Each entry carries
  `icon` and `own`. A change redraws the cached entries' icons in place rather than forgetting them, since their URL
  and version still hold.
- **Shell.** `ResultActions`, `OpenWithMenu` (through `FilesScreen`) and `IconImages.app` ask `AppDirectory`.
  `IconImages` is a static utility used deep in view code, so `AppController` points its `apps` at the directory
  rather than threading it through every renderer. `PluginTileImage` is now `@MainActor` for the same call. The well's
  image comes from the store's `[icons]` and `TileIconFiles`' observed shims rather than from `AppDirectory`'s cache,
  because the cache is updated by the store's observer a turn after SwiftUI redraws. The picker's colour and fill live
  in `SettingsNavigation`, so they last until the window closes, as the product says. A popover loses its window's key
  status to the Open panel and closes, so a chosen pack or a refusal sets the row open again.
- **Fixtures.** The design had two catalogs committed. A pack of two empty `.icon` documents compiles to 3.2 MB:
  actool renders incompressible flat fallbacks at 1024 px for each appearance, and a transparent fill was still
  2.8 MB. So `make fixtures` compiles them into `.build/fixtures` from sources committed beside the tests, as `make
  plugins` builds the test guest. `make test` depends on it, and CI's runner has Xcode. The Makefile already had an
  `ACTOOL` of its own for the app icon, which a variable of that name would have overridden; the fixtures use
  `COMPILE_ICONS`.

Verified on a debug build in the `golden-gate-base` VM (macOS 27.2), with a config holding every shape:

- **Tiles and the puck:** a filled picture on Files, a pack's icon on Safari, an unfilled picture on Notes, a catalog
  of one on TextEdit, a missing file on Maps (own icon and the diagnostic) and a picture on the sidelined Preview.
- **Elsewhere:** search's app rows and Open With in Files wore the given icons.
- **Change Icon…:** from a pinned tile and a running one, it opened Icons at the row, scrolled to, with the picture's
  colour and fill taken up.
- **The picker:** choosing a picture, the fill and the own icon wrote, rewrote and removed the line.
- **Choose File…:** a pack from outside the settings folder opened its grid, and its icon was named against the
  `icons/pack.car` already there by hash. A flat catalog was refused with its reason and not copied.
- **Outside Settings:** a hand edit redrew the dock live, and a relaunch drew everything at once and pruned the shim no
  longer named.

## Observations

- Not driven: a `.car` dropped on a well, Other App…, the colour well dragged, a minimised window's corner, and a
  plugin's view naming an app. Only macOS 27.2 was tested; Tahoe was not.
- Cairo's pictures are drawn in the Default style only (design's _Pictures in the other styles_). Whether a switch of
  the system's style redraws catalog icons while dock2 runs is unmeasured.
- An entry written as its own table, `[icons."com.apple.Safari"]`, is read, but Settings cannot replace it: the write
  is logged and dropped. A catalog replaced at the same path is read again only on a change to `[icons]` or a launch.
- `dock2 config check` reports `[icons]`' shape mistakes, but not a missing or refused file, which needs
  `TileIconFiles`.
