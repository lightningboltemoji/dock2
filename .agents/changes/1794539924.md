# Waiting for a watch to be live

> Change `1794539924` — 2026-11-12

## Goal

`release` failed at Test on `84f2885`, so nothing published. The failure was
`aWatchHearsChangesUntilItsFolderGoes`: no `changed` toast arrived within its 5 s, and 98 of 99 plugin tests
passed. The commit (pulley → cranelift) is unrelated. The test had a premise that it never checked, the same
fault `1793843665` removed from the other plugin tests.

## Implementation

The test waited for the watch's key in `resources`, then wrote `touched.txt`. `watch()` holds that key at once,
on purpose, so that a limit, a revoke or a stop counts a watch that is still resolving (as
`watchesAreCountedBeforeTheyResolve` covers). The FSEvents stream only starts later, in `startWatching`, after a
hop to `fileQueue` and back to main. On a slow runner the write could land in that gap, and a stream started
`SinceNow` never reports a change from before its start.

The real premise is a started stream, which `startWatching` records in `watched`. `watched` is now
`private(set)`, the same as `timedOut`, and both watch tests wait on it through `watching(_:)` and `#require` it,
so an unmet premise fails on its own line. `revokingFilesEndsTheWatch` had the same gap in a quieter form: when
the revoke landed while the watch was still pending, it passed without testing the end of a live watch. It now
revokes a live one and also checks that `watched` is cleared.

Proved by widening the gap: with a 300 ms `usleep` at the head of `watch()`'s `fileQueue` block, the old test
failed 3 of 3 with CI's assertion and timeout, and `revokingFilesEndsTheWatch` passed in 44 ms, during the pending
window. With the fix and the same delay, both passed 5 of 5, and the revoke test took about 350 ms because it now
waits for the stream. After the delay was removed, `taskpolicy -b swift test --skip-build --filter
Dock2PluginsTests` passed 3 of 3, at about 12.7 s against CI's 11.7 s. The failure did not reproduce in 5
unprobed runs at background priority.

Rejected: telling the plugin when its watch is live. It is the only signal a plugin could act on, but it changes
the plugin protocol to fix a test. Also rejected: rewriting the file until a change is heard, which would hide a
watch that never starts behind a timeout.

## Observations

- Not yet proven on a runner: the first proof is the next push to `main`.
- A plugin has the same gap: `watch` then an immediate write may not be heard, because it gets no confirmation
  that its watch is live. If that matters to a plugin, a `watching` event is the way to fix it.
- A revoke during the pending window is now covered only by the `pending` guard in `watch()`, not by a test of
  its own.
