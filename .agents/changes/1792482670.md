# Foundations: takeovers, settings, the stage

> Change `1792482670` — 2026-10-20

## Goal

Lay the ground the MVP stands on (`design/README.md`): a journal that can give back more than the system
Dock's two keys, since ⌘space and "Show in Finder" are takeovers too; dock2's own settings; and one window
for everything dock2 draws, so the field can later part from the platter inside one glass tree.

## Implementation

**`Dock2System`.** The system code moved out of the shell into its own module. The guard must give back
every takeover from a process with no UI, so nothing it runs may sit beside the windows.

**The journal of takeovers.** `TakeoverJournal` maps a takeover's name (`system-dock`, `hot-key.<n>`,
`file-viewer`) to the user's original state as a property list; each takeover owns its own shape
(`DockOriginal`, `HotKeyOriginal`, `DefaultOriginal`). `Takeovers` keeps the old rules: the entry is
journaled before anything changes and nothing changes when it cannot be; a surviving journal is kept, not
re-snapshotted; giving back goes system Dock last because it restarts the Dock. New: an entry a run will
not take over again is given back at launch, and an unreadable journal is rebuilt from what each known
takeover can tell of the system's current state. Version 1 files are read and replaced. The hot key table
(`SLSIsSymbolicHotKeyEnabled`/`SLSSetSymbolicHotKeyEnabled`) and the `NSFileViewer` takeover are written but
not engaged yet. Read-only, the table names entry 64 ⌘space, 65 ⌥⌘space, 52 ⌥⌘D, 8 ⌃F3 (F3 with the
function-key flag) and 1/2 ⌘⇥/⌘⇧⇥ — several of the product's unverified entries.

**Settings.** `SettingKey`s with defaults in Core; `SettingsStore` on `UserDefaults(suiteName:)`. Names
have no dots: change observation is KVO, which reads a dot as a key path, and KVO is what carries a
`defaults write` from outside.

**The stage.** Two experiments decided it, with probe apps of their own:

- *Clicks.* A borderless, non-opaque window over the desktop, part `NSGlassEffectView`, part bare, part
  alpha 0.01, part opaque: clicks on glass, the 0.01 layer and the opaque layer hit the window; on bare
  transparency they reached the desktop. A window larger than what it draws costs the apps below nothing.
- *The keyboard.* The earlier finding gave the keyboard back by ordering the panel out, which a window that
  also holds the dock cannot do. With an "editor" app in front and a key-capable non-activating panel:
  `NSApp.deactivate()` gave the editor's window key status back with the panel still on screen, and the
  next keystroke landed in the editor, every time. `orderOut` then `orderFrontRegardless` also works but
  reorders the window; `resignKey()` works and is documented as not to be called; activating the front
  app does nothing. Keystrokes were posted only while the probe editor was frontmost.

So `StageWindow` spans the screen's width from its bottom edge and `Stage` sizes its height to its
occupants; the label became a view in it.

**A testing trap.** Synthetic mouse moves seemed to show that hover was broken, before and after the
change. A single `CGEvent` move to a point moves the cursor but reaches no app's tracking areas; a path of
moves with their deltas set does. The validation tools glide now.

Verified on this Mac: tests (37); dock2 run from `.build`, the platter and label drawn from the stage
(screenshots), hover reported through the stage; SIGINT gives everything back; `kill -9` and the guard
gives everything back; afterwards `com.apple.dock` matches the backup taken before work started.

## Observations

- The system Dock's full-screen window sits at the same level as the stage and, restarted after dock2's
  window appears, in front of it. Clicks and tracking reach dock2 through its transparency, so nothing is
  done about it.
- Tile size is still mirrored from the system Dock; settings copied at the first launch come with dock
  parity.
- The hot key and file viewer takeovers are untested on the real system until they are engaged.
