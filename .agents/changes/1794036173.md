# Files reads folders off the main thread

> Change `1794036173` — 2026-11-06

## Goal

Opening a folder not yet listed held up everything, with the listing on the main thread and `showFiles` calling
`go(to:)` before it pushed the screen. A folder of 8,000 items took 700–800 ms to show a first frame in a VM, against 75
ms once listed, and the app answered nothing meanwhile. A share that doesn't answer could hold it up for as long as it
liked. `1794031560` left this as the largest latency in opening Files.

## Implementation

Timed first: `DirectoryListing.list` was 566 ms of a 569 ms `render` of that folder, and `ColumnsView.show` 0.3 ms, so
reading is the whole cost and rows need nothing.

**`FolderListings` (System)** owns reading, and tests apart from any view. `listing()` gives what is known, nil until a
first read lands. What is known stands through a refresh, where `listings[folder] = nil` used to leave a gap. A read
waits 10 ms, so ordinary folders land on the frame that asked: without that every folder would show an empty column for
a frame. Waiting on the main thread is bounded by that, where the old read was bounded by nothing.

**What assumed the answer was there.** `pruneVanished` ran straight after invalidating, so an empty answer would have
cleared the selection; a new folder's `edit(url)` silently does nothing without its row; and `enter()` selected a first
item that wasn't known yet. `whenListed` runs these on arrival. The rename waits for its row and not for an up-to-date
listing: the file watcher marks the read that already holds the row stale, and waiting for current read the folder
twice, 2.1 s against 1.5 s in the large folder. Waiters are dropped with their folder, or one would run on coming back
to it, opening a rename out of nowhere.

**Cancelling.** The first version forgot a folder and left its read running. Flipping between a large folder and a small
one 20 times left the small one on Loading… in 6 rounds of 6, its read queued behind abandoned ones, which is what
holding ↓ through large folders does. A forgotten read now stops between items. The same run lands in 33 ms.

Rejected: a timeout on the read, which would turn a slow disk into an error; showing an empty column at once for every
folder, which flickers; and reading names first with details after, which is more than this needed.

Measured in a VM on release builds, 8,000 items, before and after: first frame 693–778 ms to 83–175 ms, `dock2 files`
returning 604 ms to 58 ms, a command straight after it 51 ms to 11 ms, New Folder to its rename field 2.0 s to 1.5 s. A
small folder has its rows in the first frame, as before. Driven in that folder: a file arriving keeps the selection, the
selected file vanishing clears it, going into a folder selects its first item on arrival, New Folder starts its rename,
40 files arriving at once, 20 quick flips between folders, one process throughout.

## Observations

- Not seen on a real slow or hung share: reads that block are covered by tests alone. A hung read keeps a thread until
  it returns.
- Still on the main thread, one item each and so quick on a local disk: `go(to:)` and `reveal` reading what they were
  given, `shown` walking up a path. A share that doesn't answer can still stall those. `complete()` and search's
  `open(found)` list on the main thread too.
- Only the current tab's folders are kept, as before, so showing another tab reads its folders again, now as Loading…
  rather than a freeze.
- A rename or a move in a large folder shows the old row until the read lands, 0.6 s at 8,000 items in a VM. It used to
  freeze for that long.
- Each item costs about 0.07 ms in a VM. Which of the 12 resource keys costs most was not measured, and reading fewer
  would shorten this for everyone.
- Only macOS 27.2 was run. `tahoe-base` was stopped.
