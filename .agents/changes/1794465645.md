# Titles in sight, keywords across

> Change `1794465645` — 2026-11-11

## Goal

Two things in the Pills flow. Arrowed to the bottom and back up, the selection came to rest on `sun.max` with
"Weather" scrolled off above it: a selected item next to its heading with the heading out of sight. And "weather" found
every Weather pill, through the keyword the demo gives each one, but "weather sun" found none, since each of an item's
title and keywords had to match the whole query alone.

## Implementation

Keeping the selection in view now keeps the title it stands directly under. In `FlowView` that is a pill on its
section's first line, found by `FlowLayout.title(over:)` (Core, tested) by walking back along the line to a title. In
`RowsView` it is the row next to it on the far side, which is before it in a view and after it in search's
bottom-up rows. The title is joined to the selection's frame for `scrollToVisible`, so scrolling down is unchanged (the
title is already above the selection) and scrolling up stops one title higher. The rows were fixed too: they had the
same flaw, and the rule is one rule.

Matching moved into `Matcher.match(_:_:keywords:subsequence:)`: the best of the name alone, the query's words falling
across the name's and keywords' words together (`.words`), and each keyword alone. Ties go to the name, then to the
match across, so the name's ranges are drawn whenever its match is among the best. A keyword's exact match still beats
the name's prefix, as it did. List filtering and both command sources
(dock2's and plugins') use it, replacing three hand-rolled versions. Built-in commands used to pick a keyword's ranges
when a keyword outranked a title that also matched, which bolded the wrong letters. That case now draws nothing.

A match across fields ranks as `.words`, not as a kind of its own below it. Each query word begins a word of the item
either way, and a new `MatchKind` would reorder search across every source for a distinction no one has asked for.

Section titles are not searched themselves. A plugin that wants its sections found puts their names in its items'
keywords, as the demo does. Matching titles implicitly would make "to" match every item under a "Today" heading.

## Observations

- Tested in the golden-gate VM: Pills arrowed 30 down and 30 up returns byte-identical to its opening capture,
  "Weather" in sight. Demo List the same, with "Icons", apart from the overlay scroller. "weather sun" filters to
  sun.max, thermometer.sun, sunrise, sunset. Search's "toggle dock" finds Toggle Auto-hide through its keyword
  "hide dock".
- Search's bottom-up case (a section's top row bringing its title) is covered by the code path but was not filmed.
- The greedy word assignment can miss a match that exists, e.g. a query word taking a name word that a later one
  needed. That was already true within one name, and spreading across keywords doesn't make it worse.
- Leaving section titles to keywords was confirmed as the design, and is now stated in `product/plugins/views.md`.
