# Tahoe keeps running without the keys it lacks

> Change `1793931389` — 2026-11-05

## Goal

dock2 died on Tahoe at the first summon: `NSUnknownKeyException` for `diffuseHeightScale`, written by
`GlassLayer.rebuild` for the pane's halo. The key came with `2e114cb` and shipped in v0.4.0, which launches and shows
onboarding on Tahoe and dies once the field opens. `isAvailable` asked after classes and filters, never keys, and nothing
here could have seen it: this Mac and both CI jobs run macOS 27, and `.macOS(.v26)` says nothing about a string. The work
was to end that kind of crash and to be able to ask a macOS what it lacks, without a list of keys to keep beside the code.

## Implementation

`PrivateSurface.swift` names each private class and filter (`PrivateType`) and the keys dock2 writes on it (a `PrivateKey`
enum, each case named for its key). `Private<Key>` is an instance only those cases can write, and it skips a key this macOS
lacks. `GlassRecipe` is keyed by `GlassInput`, so a recipe can't name an input that isn't declared. `dock2 debug audit` walks
the same enums, and `PrivateType.keys` is an exhaustive switch, so a new key is audited by being writable at all and a new
type won't compile until its keys are named. The audit is in the CLI, not behind the socket, so it runs where dock2 won't.

Keys and not a write-time recording because a recording only knows what was built: the halo is on one recipe, so an audit
would need a list of recipes, the same list to forget under another name. Presence is read from a setter or `inputKeys`
and not by writing, because only the `CASDFEffect`s throw; a layer or a `CAFilter` takes any key and reads it back. So 3 of
Tahoe's 22 missing names could crash and the other 19 could only ever look wrong, which is why a launch test alone was not
enough. `isAvailable` now asks for `CASDFShadowEffect` too, which it made by force without checking. The filter's `name`
write is gone: `filterWithType:` names a filter for its type, on 26.6.2 and 27.2 alike, and `make()` relies on that for the
lens's key paths. Those paths go through `setValue(forKeyPath:)`, not `Private`, but are built from `GlassInput`, so they
are audited; an input Tahoe lacks is ignored there, and the gem played in both appearances.

The tree is unchanged on macOS 27: a throwaway test dumped every recipe in both appearances, the lens played, both mirrors
and `blendsThrough` (classes, frames, each filter's inputs, each effect's properties, animations), and 4,238 lines came
out byte-identical across the change, as two runs of the old code had. On a Tahoe 26.6.2 VM the audit named the same 22 of
93 as a separate probe. The build then went through launch, dock, summon, search, Files, Clipboard and the gem lens in both
appearances, and a first launch to onboarding, without an exception, and gave the Dock back. Before the fix the same VM
crashed at `dock2 files`, and the guard gave the Dock back then too. Screenshots of a live dock2 could not prove the change,
since two runs of one build differed in 65–99% of pixels with the person's windows moving behind the glass.

## Observations

Tahoe lacks `sourceSublayerDefinesBounds`, the three `diffuse*Scale`, and 18 `glassBackground` inputs: `MaxLuma` and
`MaxLumaSDR`, seven of the in-filter highlight, five of the ring shadow, four of the blur fill. dock2 no longer crashes for
them, but the glass is not the same glass: `dark-dock` in the VM reads close to light. Whether that is the missing `MaxLuma`
or the VM's paravirtual GPU is unmeasured; a macOS 27 VM would settle it, same GPU and another OS. No recipe is fitted to
Tahoe, and only 26.6.2 was run, of a minimum of 26.0. A name being present says nothing of what it does there. dock2's
`dlsym`'d symbols are outside the audit; they already fail to `nil`. `Dock2Shell` has no test target, so `Private`'s skip is
exercised only on a macOS that lacks a key. A second `PrivateKey` enum on a type that has one wouldn't be audited.
