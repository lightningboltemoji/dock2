# An app quitting mid-launch

> Change `1793677193` — 2026-11-02

## Goal

dock2 crashed when a regular app left `runningApplications` before it finished launching. That happens rarely
enough that dock2 ran for a day or two at a time, and since the guard gave the Dock back, the crash read as dock2
quietly vanishing. The one report on disk (2026-11-01, after 32 hours up) faults on the main thread in
`-[NSRunningApplication removeObserver:forKeyPath:]`. The call comes from an `NSKeyValueObservation.Helper` torn
down inside `-[NSRunningApplication dealloc]`, when a LaunchServices notification block pops its autorelease
pool.

## Implementation

`RunningApps` observed `isFinishedLaunching` on each app still launching, and kept the token but not the app.
Swift's KVO ties its helper to the observed object as an associated object. When the app died mid-launch,
LaunchServices' block released the last reference to the list's instance one main-queue turn before the
`refresh()` that would have dropped the token. The instance was freed while still observed, its helper
unregistered on the way out, and `NSRunningApplication`'s own `removeObserver:forKeyPath:` read freed state.

Now `RunningApps` observes no app. `NSWorkspace.didLaunchApplicationNotification` triggers `refresh()` a turn
later, as the list's own KVO does, and `launches` is gone. A probe watched both mechanisms across nine
launches: Calculator, TextEdit, Chess, Stickies, Dictionary, Font Book, Script Editor, Preview, and Calculator
again with `open -g`. Each time the note and the flip of `isFinishedLaunching` came within 6 ms of each other,
in either order. The note carries a different instance from the list's. When the note arrived, the list's
instance still said unfinished in five of the nine; one turn later it said finished in all nine, hence the
hop. The note never came for an app that died mid-launch, or for any accessory or background-only process in
the run, so nothing needs forgetting.

Rejected: keeping per-app KVO, but holding each app beside its token and invalidating before letting it go.
That fixes the crash but keeps per-app state and a lifetime to get right, for a fact `NSWorkspace` already
broadcasts.

**Validation.** Two test apps, both built in the scratchpad. `Stall` checks in as a regular app
(`NSApplication.shared`, `.regular`) and never runs, so it is listed and never finishes. `Slow` runs three
seconds after checking in and starts nothing else. Two other ways to get an app that never finishes launching
don't work: a shell-script bundle never checks in, so LaunchServices never lists it; and killing Chess on a
timer lands before it checks in or after it has finished.

- `Stall`, killed with `kill -9` two seconds in: HEAD's debug build died with the report's stack, and the guard
  gave the Dock back and removed the journal. The fixed build stayed up through four kills and never logged
  "deallocated while observers are still registered".
- `Slow`, recorded on the display at 4 fps with the dock held up: the probe logged no list change between
  `Slow` appearing and finishing, so only the note could stop its hop. The tile hops from appearing (≈1.25 s)
  until it finishes (≈4.3 s), then rests. Calculator hops once and rests, and `Stall` hops on.
- `make test` passes.

## Observations

- A tile whose app quits mid-launch hops on until the 15 s fallback (read from the code, not filmed).
  `DockController.runningChanged` stops only apps that are listed and finished, and an app not yet listed
  can't be told from one that died. `didTerminateApplicationNotification` would tell them apart.
- `RunningApps.isLaunching(_:)` has no caller.
- Only one crash report was on disk, so not every disappearance before this one is known to be this crash.
- `/Applications/Dock2.app` (built 2026-10-25) carries the bug until it is reinstalled.
